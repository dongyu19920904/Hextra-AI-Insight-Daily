## Today's Main Recommendation

### Check Whether Developers Using Claude Code Have Accidentally Committed Credentials Along with .claude Files

**There are specific file paths, a reproducible mechanism, and primary research — this is the most actionable starting point today.** Apiiro discovered 1,122 `.claude/settings.local.json` files in public repositories containing real credentials. The trigger mechanism is that after a user "permanently approves a command containing secrets," that command gets written to the file and then exposed publicly along with the commit.

- **Evidence and credibility:** Medium. [Apiiro research report: the discovery mechanism and file paths proving 1,122 public files contain credentials](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again) provides a reproducible audit path. Gap: the candidate inputs for this round did not include interviews with affected developers or any record of willingness to pay — whether this converts to sales still needs validation.
- **Target pool and manual approach:** Unvalidated assumption: independent developers or small teams actively pushing commits with Claude Code may not know that `settings.local.json` can be exposed publicly with the repository, and the current manual workaround may be relying on memory to judge which files are in `.gitignore`.
- **Minimum deliverable:** "Claude Code Credential Leak Self-Audit Kit" — ① an executable self-audit script (scans `.claude/settings.local.json` for credential patterns); ② a remediation checklist (adjusting `.gitignore`, removing already-committed files, rotating potentially leaked keys); ③ a documentation note (clearly stating it does not include security penetration testing or contacting leak platforms). Buyers can run the script themselves and work through the checklist.
- **48-hour validation:** First, do a complete run in a test repository and document whether the script correctly identifies issues and where it fails (sample). Then send the screenshot to 3–5 developers who use Claude Code and ask directly: "Did you know about this issue? If someone audited your repo and gave you a report, how much would you pay?" Observe whether anyone asks about pricing or says "I want to check my own repo."
- **First sale and repeat business:** Test pitch: "Have you ever pushed code with Claude Code? I'll audit your .claude files, produce a report, and deliver within 30 minutes." First sale fixed scope: audit only one specified repository, deliver a findings report and remediation checklist, no ongoing monitoring or penetration testing included. Repeat business is weak — this is more of a one-time transaction; the "common leak patterns list" can be built up as distribution material to lower the cost of similar future deliveries.
- **Risks and stopping conditions:** Compliance risk is medium — the script reads credential content, so buyers must be clearly informed that it "runs locally only and does not upload data." If buyers are concerned about an external party accessing their repository, the trust barrier will block conversion. Stop conditions: 5 target users have seen the sample and no one asks about pricing; the test environment produces too many false positives to yield a credible conclusion; or a buyer demands a guarantee of absolute security after remediation (out of scope — stop).
